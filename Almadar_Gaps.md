- **G-ORBITAL-GAME-RENDERER-019** [mechanical] — `orb validate` accepts a shader material whose WGSL the renderer's own compiler refuses. The mapper's `check_surface` runs naga only when the scene is mapped, so a program with a `draw-mesh` `material.kind: "shader"` validates at 0 errors and then paints nothing: the canvas reports `3D canvas contract is unsupported: drawables[0].material.wgsl: error: name `handle` is a reserved keyword` in the page and every drawable of that canvas is lost. Seen 2026-11-12 on `osama-jazari` (a local named `handle`); Chrome's own compiler had accepted the same source, so a browser check does not stand in for naga either (the reverse of G-ORBITAL-GAME-RENDERER-017). Fix: validate runs `check_surface` on every literal `material.wgsl` (a std lint over the lint index calling the same naga check, or the check lifted where L2 can reach it), so the author sees the compiler's line at author time. orbital-canvas, almadar-std. Reproduce: a shader material whose `shade` declares `let handle = 1.0;`, then `orb validate`. Prevention rung: (2) `orb validate`.
  Severity: medium. Root cause: one-off.

- **G-ORBITAL-GAME-RENDERER-018** [architectural] — Canvas text is drawn only in the crate's bundled faces, whatever the theme says. `vector.rs` carries DejaVu Sans, Noto Sans Arabic (regular and bold) and DejaVu Sans Mono; `parse_text_font` (`mappers/game_canvas_2d.rs`) accepts `sans-serif`, `system-ui` and `monospace` and refuses every other family; `add_font_face` takes a host face only for a script no bundled face covers, and the browser build does not expose it. A theme's `typeScale` families therefore never reach a `draw-text`, so a page that must follow its theme's typefaces cannot draw its words on the canvas: on `osama-site` (2026-11-11) the home page's text looked wrong beside its essays, and the owner chose to lay it over the canvas as page text. Labels that belong inside a scene still draw in DejaVu. Seen again 2026-11-12 (P-033, the Rasm kit): the Naqsh theme's serif voice (`600 26px serif`) is refused, so its looks were moved to `sans-serif` until this lands; numeric CSS weights (`600 15px sans-serif`) are read since that day. Fix: a canvas draws a named family from a face the program declares and the host supplies (the canvas theme's families, or a `fonts` list on the pattern), on every host. orbital-canvas, orbital-wasm, the shells. Reproduce: a `draw-text` with `font: "bold 20px Amiri"` draws nothing. Prevention rung: (1) the pattern's declared meaning (`font` is declared as a CSS font and reads three families).
  Severity: medium. Root cause: one-off.

- **G-ORBITAL-GAME-RENDERER-017** [mechanical] — A shader material can pass the mapper's check and still be refused by a browser. `scene3d::render::check_surface` validates `material.wgsl` with naga, and naga 26 does not require uniform control flow for derivatives in a fragment stage (`valid/analyzer.rs`, `DISABLE_UNIFORMITY_REQ_FOR_FRAGMENT_STAGE = true`), while Chrome's WebGPU compiler does: `fn shade(px: Pixel) -> vec4<f32> { var w = 0.0; if (px.uv.x > 0.5) { w = dpdx(px.uv.y); } return vec4<f32>(w, 0.0, 0.0, 1.0); }` answers `'dpdx' must only be called from uniform control flow` there (checked 2026-11-11 through `createShaderModule` + `getCompilationInfo`). Such a shader maps as a valid scene, then fails when its pipeline is made, and a renderer failure in the browser takes the page down (G-ORBITAL-GAME-RENDERER-014). The shaders in `apps/osama/scene/shaders.py` were checked by hand against Chrome's compiler. Fix: refuse a derivative or an implicit-level sample in non-uniform control flow in `check_surface` (naga's analysis with the requirement on, or a rule of our own), so the mapper names it as `material.wgsl`. orbital-canvas. Reproduce: the WGSL above as a `draw-mesh` shader material on WebGPU. Prevention rung: (2) `orb validate` (the WGSL is a literal in the program, so a std lint can run the same check at author time).
  Severity: medium. Root cause: one-off.

- **G-ORBITAL-GAME-RENDERER-014** [architectural] — A panic inside the browser renderer takes the whole page down. The kernel and every canvas share one wasm module, so after a renderer panic each later call into it throws `recursive use of an object detected which would lead to unsafe aliasing in rust` and the client replaces the page with that error text. Seen 2026-11-11 with WebGPU hidden on a `canvas mode:"3d"` page: glow panicked at `web_sys.rs:4223` (`Tex storage 2D multisample is not supported`, the multisampled depth target, fixed the same day in `scene3d/render.rs` `depth_texture`) and the page showed nothing but the error. The trigger is fixed; the class is not: any renderer panic still ends the app, not the canvas. Fix: the canvas boundary in orbital-wasm catches a renderer failure and reports it as that canvas's scene error (the path `take_scene3d_error` already feeds), leaving the kernel usable. orbital-canvas, orbital-wasm. Reproduce: make any `scene3d` path panic in the browser build. Prevention rung: (3) the verifiers (a page whose canvas fails must still paint its other content).
  Cause: confirmed in source 2026-11-12 (`orbital-wasm/src/lib.rs:27-28` only logs a panic; no `catch_unwind` in orbital-wasm or `orbital-canvas/src/web3d.rs`; `take_scene3d_error` reports returned errors, never a caught panic). Not checked: whether `catch_unwind` works under the wasm build's panic setting. Severity: high. Root cause: one-off.

Reproduce: serve any 3D canvas behavior, open it with `Navigator.prototype.gpu` redefined to `undefined` before load. Prevention rung: (3) the verifiers.
  Severity: medium. Root cause: one-off.
