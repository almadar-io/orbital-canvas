- **G-ORBITAL-GAME-RENDERER-026** [mechanical] — The `gpu/*` host serializes wgpu error scopes with a `std::sync::Mutex` whose guard `gpu::io::scoped` holds across its two `pop_error_scope().await`s (`orbital-canvas-render` `src/gpu/io.rs`; clippy `await_holding_lock`, the one clippy finding left after the 2026-11-16 restructure). Natively each GPU operation is driven to completion on its own blocking call, so a second caller waits; on wasm, where every future shares one thread, a second operation polled while the first is suspended at its await would block on the held lock (std on wasm32 without threads panics or deadlocks instead of waiting). Repro: `cargo clippy -p orbital-canvas-render`. Prevention rung: (3) the verifiers (a wasm twin test that issues two `gpu/*` asks at once). Severity: medium. Root cause: one-off.

- **G-ORBITAL-GAME-RENDERER-017** [mechanical] — A shader material can pass the mapper's check and still be refused by a browser. `scene3d::render::check_surface` validates `material.wgsl` with naga, and naga 26 does not require uniform control flow for derivatives in a fragment stage (`valid/analyzer.rs`, `DISABLE_UNIFORMITY_REQ_FOR_FRAGMENT_STAGE = true`), while Chrome's WebGPU compiler does: `fn shade(px: Pixel) -> vec4<f32> { var w = 0.0; if (px.uv.x > 0.5) { w = dpdx(px.uv.y); } return vec4<f32>(w, 0.0, 0.0, 1.0); }` answers `'dpdx' must only be called from uniform control flow` there (checked 2026-11-11 through `createShaderModule` + `getCompilationInfo`). Such a shader maps as a valid scene, then fails when its pipeline is made, and a renderer failure in the browser takes the page down (G-ORBITAL-GAME-RENDERER-014). The shaders in `apps/osama/scene/shaders.py` were checked by hand against Chrome's compiler. Fix: refuse a derivative or an implicit-level sample in non-uniform control flow in `check_surface` (naga's analysis with the requirement on, or a rule of our own), so the mapper names it as `material.wgsl`. orbital-canvas. Reproduce: the WGSL above as a `draw-mesh` shader material on WebGPU. Prevention rung: (2) `orb validate` (the WGSL is a literal in the program, so a std lint can run the same check at author time).
  Severity: medium. Root cause: one-off.

- **G-ORBITAL-GAME-RENDERER-014** [architectural] — A panic inside the browser renderer takes the whole page down. The kernel and every canvas share one wasm module, so after a renderer panic each later call into it throws `recursive use of an object detected which would lead to unsafe aliasing in rust` and the client replaces the page with that error text. Seen 2026-11-11 with WebGPU hidden on a `canvas mode:"3d"` page: glow panicked at `web_sys.rs:4223` (`Tex storage 2D multisample is not supported`, the multisampled depth target, fixed the same day in `scene3d/render.rs` `depth_texture`) and the page showed nothing but the error. The trigger is fixed; the class is not: any renderer panic still ends the app, not the canvas. Fix: the canvas boundary in orbital-wasm catches a renderer failure and reports it as that canvas's scene error (the path `take_scene3d_error` already feeds), leaving the kernel usable. orbital-canvas, orbital-wasm. Reproduce: make any `scene3d` path panic in the browser build. Prevention rung: (3) the verifiers (a page whose canvas fails must still paint its other content).
  Cause: confirmed in source 2026-11-12 (`orbital-wasm/src/lib.rs:27-28` only logs a panic; no `catch_unwind` in orbital-wasm or `orbital-canvas/src/web3d.rs`; `take_scene3d_error` reports returned errors, never a caught panic). Not checked: whether `catch_unwind` works under the wasm build's panic setting. Checked 2026-11-13: it does not. The wasm build is `wasm32-unknown-unknown` on stable 1.93 (`rust-toolchain.toml`), where a panic aborts as a trap and nothing can be caught; an unwinding build needs a nightly toolchain and build-std, which the owner declined. What took the page down was the web client: after the trap the view's borrow stays held, so every later call on it throws, and `resize`, `setReducedMotion` and `free()` were called from React effects and cleanups with no guard, so the next commit threw and the page was replaced. Owner ruling 2026-11-13 evening: isolate the canvas in the web client. Done 2026-11-13 night, uncommitted (`renderers/web/src/lib/drawable/orbital/viewGuard.ts`, `OrbitalCanvas3D.tsx`, `OrbitalSceneCanvas.tsx`): every call on a view goes through one guard, a call that throws a `WebAssembly.RuntimeError` marks the view dead, and a dead view is never called again (frame loop, scene, resize, pointer and key input, `free`); a returned error still shows and clears as before. Tests `viewGuard.test.ts` (3), `OrbitalCanvas3D.trap.test.tsx` (3, the trap case red before) and `OrbitalSceneCanvas.trap.test.tsx` (3, the trap case red with the guard switched off). What remains, and why this is medium now: a panic taken while a borrow the kernel shares is held (the `GpuHost` the canvases and the kernel's `gpu/` asks use) still leaves that borrow held, so the kernel's next `gpu/` ask traps too and the app ends; only an unwinding build or a renderer with no panic on the draw path closes that. No panic site on the draw path was converted to a returned error tonight, and the fix was not looked at in a browser. Severity: medium. Root cause: one-off.
